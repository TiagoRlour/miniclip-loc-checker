# AI Usage & Collaboration Log

## 1. How I Used AI
- **Problem Decomposition & File Exploration:** Before writing any code, I shared the task prompt and both `.plist` files with the AI and asked it to help me dissect the requirements and manually inspect the files first.
- **Incremental Development:** Instead of asking the AI to generate the entire tool at once (which initially overwhelmed me with too much information), I pushed back and instructed the AI to guide me step-by-step: first building a minimal file loader, then adding severity buckets (`Blocker`, `Warning`, `Info`), and documenting decisions along the way.

## 2. What I Kept vs. What I Pushed Back On
- **Pushed back on (Process):** Initially, the AI gave me a massive breakdown of all regex rules and architecture at once. I rejected that approach and asked to go step-by-step so I could fully understand and verify every check myself before moving forward.
- **Kept (Architecture):** Using Python's built-in `plistlib` (zero external dependencies) and categorizing output into 3 actionable severity levels (`Blocker`, `Warning`, `Info`) rather than dumping a raw line-by-line diff.
- **Kept & Verified (Regex for Format Specifiers):** We designed a two-part regex in `extract_placeholders()` — one for valid specifiers (`%[0-9]*[@udfs]`) and a negative lookahead (`%(?![0-9]*[@udfs])`) to catch dangling `%` signs like `До начала %...` in Russian. I verified this against key `2b827952...` to confirm it caught the Russian regression while correctly identifying the French change (`% ...` -> `%u...`) as a bug fix.
- **Kept & Refined (Order-Independent Tag Checking):** When inspecting key `1981dc5a...`, we noticed German (`de`) and Turkish (`tk`) reversed the order of `A:[...]` and `B:[...]`. A naive regex list comparison would have flagged German as broken. We deliberately used a dictionary mapping tag names to option counts (`{'A': 2, 'B': 3}`) so grammatical reordering passes cleanly while still catching Turkish's missing option (`'B': 2` instead of `3`) and Italian's unclosed bracket.
- **Pushed back on (Naive String Length Check & UI Expansion):** The AI initially proposed simply flagging any translation that was longer than the base `en-US` string. I pushed back on this: in real-world game localisation, standard target languages (German, French, Portuguese, Spanish) naturally expand by 20% to 40% compared to English without necessarily breaking UI buttons. Flagging every longer string would flood the releaser with false alarms. Based on this, I decided that the tool should only warn when a string exceeds **2.5x the English length** (`len(text) > len(en_text) * 2.5`), and keep it strictly as a `Warning` rather than a `Blocker`. This reliably catches extreme expansions (like the 5.0x German text in `test_edge_cases.plist`) while letting normal linguistic expansion pass silently.
- **Pushed back on / Refined (Number Matching Edge Cases & Trade-off Analysis):** A naive number comparison flags almost every language in `9bb069bc...` as broken because European languages use commas (`0,5` vs `0.5`), write `4` instead of `4.0`, translate `"five"` into the digit `5`, or translate `"Rack 1 / 2"` into words (`"İlk / İkinci"` in Turkish). We refined `extract_numbers()` to normalize commas to floats and ignore `1.0`/`2.0` from the mandatory baseline list, isolating the two real bugs (`pt-BR` `3` vs `30`, and `jp` `4` vs `1.0`) with zero false positives. However, I critically evaluated this solution and noticed a blind spot: if a short string like `"Wait 1 second"` loses its `1` in translation, ignoring `1.0` globally will miss it. Rather than over-complicating the script with special-case heuristics, I kept the implementation clean and documented this exact strength/weakness trade-off in the `README.md`.
- **Caught & Fixed Two AI Assumptions During Testing:**
  1. *Word-order false positive in German (`de`):* Initially, the AI suggested checking `en_nums[-1] != nums[-1]` to catch the Japanese multiplier bug at the end of key `9bb069bc...`. When I ran the script, it falsely flagged German (`de`) because German syntax places `0,5` after `1,0` at the end of the sentence (`"...Minimalwert von 1,0 um 0,5 reduziert"`). We replaced positional index checking with frequency counting of significant numbers (`en_counts != tr_counts`), eliminating the German false positive while still catching both `pt-BR` (`3` vs `30`) and `jp` (duplicate `4.0`).
  2. *Literal vs. actual newlines (`\n`):* Initially, the line-break check didn't trigger on `d8225439...` (`jp`) because the `.plist` files store escaped literal `\n` characters (`\\n`) rather than raw newline bytes. Inspecting the terminal output revealed the literal `\n` in `'Play\nas Guest'`, so we updated `count_linebreaks()` to count both.

## 3. How I Verified AI Output
- Every check was built and tested incrementally against `localisations_1_2_0.plist` and `localisations_1_2_1.plist` before moving to the next check.
- I manually cross-checked every flagged key in the raw XML to ensure zero false positives on valid changes (such as the `pt-BR` typo fix `videos` -> `vídeos` in `d8225439...`, European decimal commas `0,5`, and German/Turkish tag reordering).
- I verified both failure and success boundaries using two custom test files: `test_edge_cases.plist` (catching missing `en-US` reference keys, 5.0x length overflow, and dropped languages without crashing) and `test_clean_release.plist` (verifying that a clean release exits with code `0` and a `SAFE TO SHIP` verdict).
